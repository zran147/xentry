## Verdict and Resolution Check

**What the new contracts resolve.** The runner-owned nonce, the null actor, and destroy-before-validate are the real causal controls and they survive this review. The runner-owned nonce is the correct root fix for the Stage 5 self-reporting finding. The Stage 5 working set - loopback plus SSH tunnel, the host-side PoC archive as opaque bytes with the SSRF guard connecting to the validated IP, and the isolated-network/nftables direction - remains valid. The two-VM attacker is not what makes the target-side observation independent; it is an isolation control layered on top of the nonce controls.

**What the new architecture does not resolve.** The two-VM and system-broker escalation is unconditional without the approved Phase 0 gates, decision record, or budget line (Blocker). The two-VM's causal justification is inconsistent and untested, especially for Dirty Frag (Major). The broker's privilege is not narrowed and the QEMU/domain UID is unspecified (Major). The nonce value crosses into the attacker VM and the validator (Major). The extractor/ADK pipeline and the typed pack layer have no load-bearing V1 consumer (Major x2). The state machine over-models a linear pipeline (Major). The artifact catalog is trust-on-first-use (Nit).

**V1 verdict.** Not implementation-ready. The revision added scope faster than it resolved it; no finding lowers the Stage 5 verdict, and the new Blocker widens it.

## Prioritized Findings (Blockers -> Major -> Nits)

### Two-VM and root-broker defaults bypass the approved Phase 0 gates and have no decision record or budget line - Severity: Blocker

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 9, 13, 28, 30, 63-78, 90-99, 183-200, 519-535, 585, 715`; supported by `/home/zran/ambitious_projects/xentry_claude/concepts_brief.md` lines 52, 69-73, `/home/zran/ambitious_projects/xentry_claude/consolidated_review_report.md` lines 272-273, and `/home/zran/ambitious_projects/xentry_claude/docs/designs/xentry-v1-rev1.md` line 466.
* **Discrepancy Description**: The approved V1 brief makes the target VM with a non-root actor the chosen design and the second minimal attacker VM a fallback only "if a web target cannot be validated causally"; the consolidated review leaves "whether V1 builds the second attacker VM" as an owner decision. The same approved brief says V1 tests `qemu:///session` first and uses a system-libvirt broker only "if a target needs system libvirt," with a three-verb helper (`start_target`, `exec_in_guest`, `destroy`). Revision 2 makes both the second VM and the system-libvirt broker unconditional (lines 9, 13, 28), removes the session-vs-system and one-VM-vs-two gates from Phase 0 (lines 90-99), and expands the broker to twelve verbs including `copy_in`/`copy_out`, `snapshot`/`restore`, and `read_host_evidence` (lines 183-200). The ADR that would record the change is still a Create file (line 715) although line 585 cites `docs/adr/0001-v1-reset.md` as if it exists, and the binding budget (lines 63-78) has no line for the second VM, the broker daemon, its tests, or its root systemd unit.
* **Rationale & Recommendation**: This is the scope discipline the reset was meant to preserve: a fallback promoted to default without the test or owner decision the approved plan required is silent growth, and the design pays the full two-VM plus root-daemon cost before knowing the single-VM path fails. Restore both gates as Phase 0 exit criteria with a named decision owner and a pass/fail test; record the decision in ADR 0001; and add explicit budget lines for the second VM, broker daemon, its tests, and root systemd unit. If the owner has already approved the escalation, the defect is the missing record and budget, not the choice.

### The two-VM's causal justification is inconsistent and untested, especially for Dirty Frag - Severity: Major

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 30-31, 220-232, 334-336, 508, 519-523`
* **Discrepancy Description**: The stated reason for the attacker VM is "a single VM for remote PoCs (rejected: same-kernel causality)" (line 523). But Dirty Frag is a kernel exploit, runs in the target VM with no attacker, and its decisive evidence is guest-attested with the host-channel forgery question still open (lines 96, 508). For PHP2Shell and GitLab the nonce is owned by the service user and the actor is a different unprivileged user, which the approved brief already judged workable, though weaker than a second VM. The attacker VM does not observe the nonce; the runner does (lines 30, 107). The separate kernel can add isolation, but it is not a substitute for the nonce placement, null actor, and destroy-before-validate controls. The design never states which of these is the causal proof, and it applies the same-kernel objection to remote PoCs but not to the one kernel exploit.
* **Rationale & Recommendation**: The Phase 0 causality test the approved plan required is the missing decision. Run it: validate PHP2Shell and GitLab on the one-VM design with the protected nonce and null actor, and keep the second VM only if that path fails. If the second VM stays, state it as an isolation/defense-in-depth choice rather than the causal fix, and either justify why Dirty Frag - the kernel case - does not get it or downgrade Dirty Frag's authority (for example, `guest_attested+llm_assessed`) until the host-channel forgery question is closed.

### The root broker is over-privileged and less simple than the prior unprivileged QEMU + narrow network helper - Severity: Major

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 183-200, 472-474, 531-535`; prior tree `/home/zran/ambitious_projects/xentry/src/xentry/provision_net.py`, `/home/zran/ambitious_projects/xentry/docs/vm-builder.md` lines 120-123, `/home/zran/ambitious_projects/xentry/docs/base-images.md` line 150; revision 1 line 466.
* **Discrepancy Description**: The broker is root-owned and exposes guest-root `exec`, `copy_in`/`copy_out`, `start_*`, `snapshot`/`restore`, and `read_host_evidence`. Line 200 says it validates job id, profile id, and host path, but not `image_id`, `vm_id`, `user`, `argv`, or `guest_path`. The design never states the domain process UID, seccomp/AppArmor profile, or whether QEMU runs as `libvirt-qemu` or root. The prior review treated system QEMU as root - "a guest root shell becomes host file access" - and revision 2 moves to system libvirt plus a broker without answering it. The prior tree already runs QEMU unprivileged (`docs/base-images.md` line 150) and uses a narrow `sudo -n boxes net provision-up` / `provision-tap` helper for the network only (`provision_net.py` lines 71-81; `docs/vm-builder.md` lines 120-123). Revision 1's Alternative 17 said "Revisit if the libvirt harness exceeds its schedule; the old QEMU code remains a reference, not a dependency" (line 466); revision 2 deletes that alternative and adds the root broker plus two-VM harness - the exact schedule risk the trigger names. This extends the Stage 5 reuse Major with new evidence; it does not restate it as a separate defect.
* **Rationale & Recommendation**: A root broker that can run arbitrary commands as root in a guest and read host evidence is a larger trust surface than the prior unprivileged QEMU plus narrow network helper; the claimed benefit over a libvirt-group user is only the fixed XML/path validation, which is unspecified. If the domain runs as root, a guest escape is host root, defeating the VM boundary. State and test the domain UID, cgroups, seccomp, and AppArmor/SELinux in the broker gate; evaluate session libvirt plus the prior narrow network helper as the default; keep the broker only for capabilities that require it. If it stays, restrict `exec` to typed pack-validated commands and a user allowlist (root only for the declared Dirty Frag step), validate every id and path, state the socket owner/mode/peer UID, and add a broker version/change-control rule so a verb-set change forces re-review. Run the reuse spike as a Phase 0 exit criterion and cite the prior files and ADR 0007 in Additional Resources.

### The nonce value's secret boundary is unenforced across the attacker VM and the validator - Severity: Major

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 334-336, 340-350, 352-356, 378`
* **Discrepancy Description**: G6 says the nonce is placed where the actor cannot read it directly, and line 355 keeps it out of the setup-author prompt. But `ProbeContext` bundles `nonce` and `nonce_path` in one object (line 350), and the attacker runs the PoC with the nonce path / `--cmd` (lines 334-335); no rule says the attacker VM, its argv/env, or the PoC template receives only the path. If the value crosses into the attacker, the PoC can echo it without exploiting, and the `response_parse` probe (the GitLab path) can become forgeable if the attacker controls the parsed response. Line 355 also says "The validator may see the nonce value only as a runner fact," and line 378 only "prefer[s]" hashes; the one 128-bit secret that anchors the causal claim is sent to DeepSeek by default-allow.
* **Rationale & Recommendation**: The nonce is the only causal anchor; its value must be runner-only. The attacker VM is where untrusted PoC code runs, and the validator is a third-party model. A "prefer" is not a boundary. Split the context into a runner-only secret and an attacker context with `nonce_path` only; make `poc.invocation_template` accept only the path; add a test that the value never appears in any attacker argv, transcript, or `copy_in`; send only `nonce_observed` and `nonce_sha256` to the validator and forbid the value in the audit bundle.

### The extractor/ADK pipeline has no load-bearing V1 consumer - Severity: Major

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 27, 48, 55, 152-153, 250-251, 358, 382-390, 737-741`
* **Discrepancy Description**: All three V1 targets are `script_source: checked_in`, and the generated path plus `author_setup`/`repair_setup` are V1.1 (lines 29, 358). The runner's `planning` state is triggered by "Setup author/repair" (line 251), but no V1 target reaches it. The extractor's `Facts` - product, range, version evidence, port, auth, build strategy, PoC context, marker, artifact candidates - are fixed in the pack, the checked-in script, or the pinned PoC. The pack has no `expected_version` field, and the `ready_target` "Version/precondition" check (line 255) could be a pack field instead. The only V1 output is the non-authoritative agent summary. V1 still pays for ADK + LiteLLM, `prompts/extract.md`, `setup.md`, `repair.md`, `src/xentry/agent.py`, the 20-fixture ADK gate, the prompt-injection corpus, the 150k token cap, and the extraction state.
* **Rationale & Recommendation**: YAGNI. The revision correctly cut the generated path but left the model pipeline that only the generated path needs. The prior tree's ADR 0007 already chose an explicit Python state machine plus a small `httpx` client over an agent framework, and the approved brief says a reversal needs a new ADR; revision 2 records neither. Cutting the extraction/authoring/repair path is the cheapest way under the 26-module budget and removes the main DeepSeek egress and prompt-injection surface. For V1, delete those states and `AgentRuntime`, add a static `expected_version`/precondition to each checked-in pack, and keep only the independent validator (or make it a deterministic rule plus an optional explanation). Move ADK, prompts, fixtures, and the token cap to V1.1 with the generated path and a fourth target.

### The typed target-pack abstraction is premature for three checked-in targets - Severity: Major

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 29, 56, 304-336, 592, 616-653, 706`
* **Discrepancy Description**: The pack schema - 20+ fields plus `pack_version`, `retry_policy`, `destroy_policy`, `what_proves`/`what_does_not_prove` - and the per-target `pack.yaml`, `probe.yaml`, and `poc.pin.yaml`, plus the shared `profiles/attacker.yaml`, `profiles/network.yaml`, and `config/artifacts.yaml`, form a four-source configuration layer for three fixed targets. The runner still selects probe primitives by `kind` (line 340) and the lifecycle by `poc_context` (lines 222-240); target branching is moved from Python into YAML, not removed. The only stated reason is V1.1 - "Add more target packs without changing the pipeline" (line 592) - but the generated path and a fourth target are deferred. `pack_version` has no migration or compatibility rule; `tests/test_packs.py` is the only consumer of the no-target-id rule; Non-Goals line 56 already excludes "Dynamic target packs or a plugin loader."
* **Rationale & Recommendation**: With all scripts checked in, a `Target` dataclass and three Python instances - already anticipated by `src/xentry/models.py` (line 658) - give type checking, no YAML loader, no schema-version policy, no pack/artifact/profile precedence rules, and no pack fixtures. The pack is only needed when generated scripts and a fourth target make the pipeline data-driven. Stage 7's Blocker is that the schema cannot express the three packs; the simpler fix is to delete the schema, not expand it. Define one `Target`/`Probe` Pydantic model with three checked-in instances in `src/xentry/targets.py`, and collapse the per-target YAML and shared profiles into those instances plus one constants module. Keep the pack schema as a V1.1 design input; if it is retained, publish a real JSON Schema and a precedence rule, but do not count it as V1.

### The runner state machine models a fixed linear program as 22 job states - Severity: Major

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 244-272, 396-409, 448`
* **Discrepancy Description**: The table has 22 states and a four-column transition table for a single-worker, single-job pipeline with two conditional branches (remote vs local). `creating_network`, `creating_target`, `provisioning`, `ready_target`, `creating_attacker`, `ready_attacker`, `freezing`, `running_null`, `restoring`, `running_poc`, and `collecting_evidence` are resource steps, not job outcomes; `done` duplicates `completed`; `failed`, `cancelled`, and `interrupted` are outcomes the table also uses as states (the Stage 5/7 contradiction is a separate defect). `vms.state` duplicates part of the resource state, and the network has no state table, so its lifecycle is forced into the job state.
* **Rationale & Recommendation**: A step-list runner - ordered `Step(name, run, cleanup)` entries plus `outcome` (`completed|failed|cancelled|interrupted`) and `cleanup_state` - expresses the same pipeline with fewer states, makes destroy-before-validate a property of the list, and removes the terminal/loop ambiguity at its root. The current model is a bespoke state machine for a program that never branches except on `poc_context`; it is the kind of premature modeling the 5,500-line budget cannot absorb. If the state table is retained, collapse the resource states into a `step` field and add the missing reboot/nonce steps.

### The artifact hash catalog is trust-on-first-use - Severity: Nit

* **Reviewer Lens:** `egm-zoom-out`
* **Affected Scope:** `Lines 99, 627, 632`
* **Discrepancy Description**: `scripts/fetch-artifacts.sh` "Fetch[es] and hash[es] the base images, attacker image, GitLab `.deb`, and Dirty Frag kernel package into the tracked catalog," and Open Question 99 asks "What exact SHA-256 values will the operator record." The pins are therefore produced by the same unverified fetch they are meant to pin, and the mirror then serves those artifacts to guests.
* **Rationale & Recommendation**: A MITM or upstream replacement at first fetch becomes the trusted pin; the artifact chain is the root of the VM boundary. Seed the catalog from vendor-published checksums/signatures, verify them in CI, and make the fetch script refuse to write a new pin without an out-of-band value; record provenance (URL, date, signer).
