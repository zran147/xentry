**What this proposes**

xentry V1 is a local web application for one or two users. It accepts a CVE link and a PoC link, fetches and stores a bounded evidence bundle, and uses a DeepSeek-backed Google ADK agent to extract typed facts and, in the Overview, author a setup script and PoC wrapper. A runner-owned pipeline provisions a target VM and, for remote PoCs, a lightweight attacker VM through a root-owned system-libvirt broker with a fixed verb set, an isolated network per job, and nftables default-deny. Three Linux targets are supported (PHP2Shell, GitLab, Dirty Frag); setup scripts are checked in and hash-pinned, and generated setup is deferred to V1.1. The runner owns fetch, plan, VM creation, provisioning, nonce generation, null-actor and real-actor runs, evidence capture, destroy, and validator invocation; the model has no execute, validate, or destroy tools. Evidence is a fresh 128-bit nonce that the actor cannot read directly; a null actor must not observe it, and a separate context-isolated LLM labels the verdict `llm_assessed`. For remote PoCs the attacker runs the PoC and the runner observes the target-side nonce; Dirty Frag uses a host-side serial/QMP channel because the guest kernel is compromised. Fourteen goals cover local operation, bounded input, runner ownership, two-VM isolation, target packs, causal evidence, job lifecycle, storage and audit, honest UI, budgets, testability, operational readiness, and scope discipline. Non-goals exclude general CVE coverage, containers, concurrent jobs, deterministic validators, generated scripts, and production-risk claims. The binding budget is 5,500 Python lines in 26 modules, 1,200 template/static lines, 3,500 test lines, 14 direct dependencies, three packs, 100 GB disk, per-target time caps, and 150,000 tokens per job over ten weeks. Acceptance requires two clean runs per target with the nonce observed, a failing null actor, and validator, ADK, prompt-injection, kill-restart, and broker gates.

**How the existing system works, per this document**

No system exists yet, so "existing" here means the planned V1 baseline; the prior v2 is described only as a failed 12,000-line predecessor. The Technical Plan defines a browser, an unprivileged web/API process, a SQLite index plus per-job attempt directories and append-only JSONL, one worker job runner, a broker client over a Unix socket, a root-owned broker controlling libvirt domains, isolated networks, nftables, snapshots, guest exec, and host evidence, and a direct-LiteLLM validator. The runner state machine runs queued through done with terminal outcomes and separate verdict/authority projections; a closed reason-code table supplies retry and next-action policy. Packs are typed manifests for three targets, and probes are one runner-owned primitive per kind. The Detailed Plan fixes Python 3.12, uv, FastAPI, Jinja2, sse-starlette, httpx, Pydantic, PyYAML, google-adk, litellm, libvirt-python, and asyncssh; host prerequisites include KVM, libvirt 12+, QEMU 10+, nftables, cloud-image-utils, qemu-img, ssh-keygen, systemd, and an unprivileged xentry user. It enumerates files for config, models, database, security, events, queue, runner, broker client, cleanup, fetch, sources, evidence, packs, agent, validator, bundle, preflight, web routes and SSE, VM driver, probes, images, a root broker service, templates, static assets, tests, and docs. Verification uses uv sync, compileall, pytest, ruff, mypy, 80 percent coverage, plus broker, network, two-VM, Dirty Frag, security, recovery, acceptance, and UI checks. Phases run one week for the broker and spikes, three weeks for engine/UI/PHP2Shell, two weeks for GitLab, two weeks for Dirty Frag, and two weeks for hardening and full acceptance.

**Findings**

1. **Major — lines 9, 27, 29, 251, 358 (setup authoring).** The Overview and G3 say the agent authors the setup script and wrapper and that the model is used for setup authoring, while G5, the nonce section, and the Detailed Plan say all three scripts are checked in and hash-pinned and generation is V1.1. The state machine still runs a `planning` state triggered by "Setup author/repair" and the agent runtime still defines `author_setup` and `repair_setup` without saying when they execute. A fresh implementer cannot tell whether `author_setup` is dead code, a fallback, or a test-only path.

2. **Major — lines 30, 334-336, 355, 186-197 (nonce placement).** Nonce timing is stated as after provisioning in G6 and after the freeze in the nonce section, and the pack declares path, owner, and mode while the runner is said to place it. The broker interface has no write-file, chmod, or chown verb; `copy_in` and `exec` are the only plausible primitives, and neither is specified to set ownership or mode. The implementer must invent how a 128-bit secret is placed for the web user or `git` without exposing it to the actor.

3. **Major — lines 31, 238, 336, 345, 354, 356 (Dirty Frag privilege).** Dirty Frag is described as running as a non-root actor, while the pack says the runner drives a "PTY root shell" and `pty_session` opens a PTY "as the actor." It is unclear whether the PTY is opened as `xentry` and upgraded by the exploit or opened as root; a null actor cannot reach a root shell, so the requirement that it exercise the same probe read path is unsatisfied. The "restore or fresh boot" choice at line 238 leaves a second implementation decision open.

4. **Major — lines 213-216, 225, 234 (network reachability).** The network block sets "host route: none," yet the same section requires a host-local artifact mirror and a "runner's probe path," both of which need host-to-guest connectivity. No mechanism is given for serving the mirror or probing the target under that rule, and a "probe path" is not a port nftables can allow. Provisioning and evidence capture therefore rest on an unresolved contradiction.

5. **Major — lines 88, 189, 200, 472 (broker command control).** The broker exposes `exec(vm_id, user, argv, tty, timeout)` with arbitrary argv and an arbitrary user, while claiming it rejects arbitrary commands outside fixed domain templates and that all VM operations go through fixed verbs. Nothing defines an argv allowlist, a restriction on the `user` argument, or how root exec is prevented. A fresh implementer cannot implement the stated broker guarantee from this interface.

6. **Major — lines 236, 263-270 (state transitions).** `destroying` transitions to `validating` or `failed`, so `cancelled` and `interrupted` jobs that enter `destroying` can reach validation despite being declared terminal. `completed` transitions to `done`, but `done` has no state row, trigger, or guard. The Dirty Frag lifecycle requires a reboot after kernel provisioning, yet the state table has no reboot state or transition.

7. **Major — lines 77, 125, 272, 290-300 (failure classification).** A destroy failure is called `security_cleanup_failed` in the state-machine text and CUJ 4, while `teardown_failed` is defined for generic destroy or network cleanup failure; the boundary between them is never drawn. Likewise, `nonce_not_observed` permits one rerun for transient infrastructure failure and `exploit_failed` permits none, but both are triggered by the same observation of a PoC run without the nonce. The implementer must invent both classifications, and they decide whether a failed run is retried.

8. **Major — lines 82, 270, 357, 371, 378, 448 (authority semantics).** The runner stamps `authority = runner_observed+llm_assessed` on every validation, even when `nonce_observed` is false and the verdict is `not_reproduced` or `inconclusive`, so the label can assert an observation that did not occur. The authority vocabulary is not closed: jobs can show `runner_observed` alone, and the validator's verdict enum omits `not_run`, which the runner can write to jobs. UI and acceptance checks need an enumerated value set and a rule for each verdict.

9. **Major — lines 29, 308-330 (pack schema).** The pack "manifest" is pseudo-YAML: entries such as `base_image: {name, url, sha256}` list field names without values, and `fresh_vm_on_retry: bool` supplies a type rather than a value, so the block cannot be loaded as a usable manifest. Required versus optional fields, defaults, and the G5 "claim limits" key are absent, and `what_proves`/`what_does_not_prove` are never related to claim limits. A fresh implementer must invent the schema, defaults, and validation rules.

10. **Major — lines 9, 17, 22, 48, 96, 347, 583-586 (undefined terms and links).** First uses of ADK, QMP, "harness," and "the bank"/"five CLI bank verbs" carry no expansion or link, so the Overview and non-goals are not self-contained. The Additional Resources section names files and "the five stage reports" without paths or links, leaving them unresolvable from the document. In the packs, "actor," "attacker," "web user," and "service account" are used closely enough together that the nonce-access rule is hard to reconstruct.

11. **Major — lines 65, 88, 600, 629, 656-688, 722-725 (budget and dependencies).** The binding budget allows at most 26 handwritten Python modules, but the file plan lists 33 Python modules excluding package markers, or 36 files including scripts. The fixed dependency list omits `uvicorn`, which `run-dev.sh` invokes, and omits the pytest, ruff, mypy, and coverage tools used in verification. It also includes `libvirt-python` without assigning it to the app or broker environment, although the broker gate says the app cannot open libvirt.

12. **Major — lines 83, 423-433, 732 (acceptance traceability).** Acceptance says no completed job may lack a validation row "tied to its nonce," but the `validations` table stores only a `runner_nonce_observed` boolean and an unspecified `evidence_json` blob, with no nonce value or hash column. The verification plan cites a "budget gate" that does not appear in the acceptance list. These criteria cannot be traced or checked as written.
