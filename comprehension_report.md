**What this proposes**

xentry V1 is a localhost web app for one or two users: they submit a CVE link and a PoC link, a deterministic runner fetches a bounded evidence bundle, a DeepSeek-backed ADK agent extracts facts and writes a setup script plus PoC wrapper, and a single libvirt/KVM VM is provisioned, frozen, checked with a fresh nonce and a null actor, then used to run the pinned PoC as a non-root guest actor. A separate tool-less DeepSeek session, with no generator history, returns `reproduced`, `not_reproduced`, or `inconclusive`; the verdict is labeled `llm_assessed` and is explicitly not deterministic proof. V1 is scoped to three Linux targets, one VM and one worker at a time, no containers, SQLite as a rebuildable index with the job directory and JSONL as authority, an honest UI separating state, verdict, and authority, and hand-reviewed bootstrap scripts followed by an autonomous generated flow; the narrowing is justified by the failed roughly 12,000-line v2 design.

**How the existing system works, per this document**

The document describes a ground-up build; the only prior system it names is the rejected v2 tree (roughly 12,000 lines, about 20 subsystems, Postgres/Alembic), used as reference only. The second range is the build plan: Python 3.12 with FastAPI, Jinja2, `sse-starlette`, `httpx`, Pydantic, PyYAML, `google-adk` plus `litellm` for the two generator calls, a direct LiteLLM validator call, `libvirt-python` and `asyncssh`, one process with a background worker, and SQLite plus per-job JSONL. It gives eight implementation steps, fixed defaults, a file-by-file task list, and verification gates: pytest with an 80% coverage floor, ruff/mypy, SSRF/security/prompt-injection tests, kill-and-restart, an environment-gated libvirt smoke test, two clean end-to-end runs per target, a dummy-pack test, a 20-scenario ADK spike, and Phase 0 gates.

**Findings**

**1. Major — ADK and LiteLLM are undefined, and the tool gate contradicts the no-tools design.** Lines 9, 66, 289-296, 460, 710. "ADK" is never expanded and LiteLLM is never defined or linked. The gate deciding whether ADK survives is a "tool-call threshold" measured with "20 scripted scenarios with two tools", yet both generator calls and the validator are said to have no tools. The two tools, the metric, and the numeric threshold are never given.

**2. Major — "The runner invokes the validator unconditionally" contradicts the null-actor short-circuit.** Lines 160 and 222. A null actor that yields the nonce "fails the job before the LLM validator", so validation is conditional. The null actor itself is never defined operationally: what it executes, as whom, and what evidence it records.

**3. Major — Dirty Frag snapshot restore conflicts with the fresh-VM retry rule.** Lines 166-167, 219-223. "Any retry gets a fresh VM because the page cache is contaminated", but the standard verification path runs the null actor and the real actor in the same VM separated only by a snapshot restore. The document never says whether a snapshot revert clears the contaminated page cache or whether Dirty Frag needs a different sequence.

**4. Major — "Plan" carries three meanings, and the `planning` phase is undefined.** Lines 34, 152, 173, 226, 614. It means the UI pre-run plan, the `planning` job state, and the generator's plan withheld from the validator. No input, output, or actor is described for the `planning` state, and the goal-level runner sequence omits it.

**5. Major — State-machine transitions are ambiguous.** Lines 149-160. The diagram does not say whether `completed` is transient while `done` is final, whether `destroying` is a displayed state, how cancellation from arbitrary states is represented, or how `interrupted` set at restart moves to teardown. `tests/test_state_machine.py` requires "allowed transitions", which are not enumerated.

**6. Major — Verdict, authority, and failure-code storage are under-specified.** Lines 30, 35, 87, 158, 233, 304-311. Line 158 calls the verdict "a separate field", but the `jobs` table has no verdict or authority column and an undefined `result` column; `validations.verdict` holds the verdict and the "projection" rule is asserted, not described, including for jobs with no validation row and for `not_run`. G11 promises a closed reason-code set, but only `security_cleanup_failed` is named, and CUJ 3's "teardown failure otherwise" implies an open set.

**7. Major — The autonomous generated flow is never exercised in V1.** Lines 13, 29, 38, 207, 593-594, 709. All three real packs are `prebuilt`; the only `generated` pack is the test-only dummy whose probe returns canned evidence. A pytest cannot demonstrate "no human review" or that an LLM-authored setup script provisions anything, so G14's central claim has no described end-to-end test.

**8. Major — The pack contract is only a list of names, and "does not branch on target ids" conflicts with per-pack Python.** Lines 197-207, 584-594, 619. No types, formats, required fields, or semantics are given for `probe.nonce_placement`, `command_or_http_request`, `expected_evidence`, `what_proves`, or "optional hand-written hooks". `packs.py` imports each pack's target-specific `probe.py` and executes it on the host, which the document neither reconciles with the no-branching claim nor treats as a trust decision.

**9. Major — Phase 0, Phase 1, and Phase 2/3 are never defined.** Lines 524-531, 538, 563, 711. The implementation order has eight steps, but the plan references phases with no mapping. The one-week ADK spike appears only in Alternatives and Verification, not in the eight-step order.

**10. Major — "Attempt" is ambiguous.** Lines 164-167, 306, 316, 614. It is unclear whether an attempt is a job, a phase, or a retry. `jobs.attempt_dir` is a single column and the directory is called "per-job", yet every retry gets "a fresh attempt directory" and the previous failure is recorded elsewhere unspecified.

**11. Major — Host prerequisites and the libvirt contingency are unstated or self-cancelling.** Lines 9-13, 269, 336, 453, 558, 707, 538. The plan assumes WSL2, `/dev/kvm`, libvirtd, systemd, and nested KVM but never states the supported host up front. If the Phase 0 session-libvirt gate fails, the only fallback, the root-owned broker, is declared "out of scope" for V1, so the reader cannot tell what ships in that outcome.

**12. Major — The API surface has no read path for validations or evidence.** Lines 175, 178-189. Job Detail must show the verdict, reason code, evidence references, nonce id, version/precondition evidence, and agent summary, but no endpoint returns validation rows or evidence; `GET /api/jobs/{id}` is only "job row plus latest state".

**13. Major — Actor identities are partly undefined.** Lines 211-213, 245, 581-592. Only PHP2Shell names its actor (`xentry`). GitLab says only that the actor is not the GitLab service user; Dirty Frag names no actor. "The web user", "the GitLab service user", and "git-owned nonce" are used as if defined.

**14. Major — The plan mixes a ground-up build with edits to existing files, and several references cannot be resolved.** Lines 17, 466, 556-557, 554, 701, 509, 694-697, 508. `.env.example` and `.gitignore` are "Modify" although the project is new; "pin exact versions in the lockfile" has no lockfile artifact and the build uses `pip install -e '.[dev]'`; `docs/adr/0001-v1-reset.md` is both an existing Additional Resource and a Create; "the old ADR 0007" is unidentified; `design_draft.md`, the `docs/designs/SITEMAP.md` convention, and the path of `concepts_brief.md` are undefined.

**15. Major — LAN access is contradictory.** Lines 25, 42, 99, 349, 542. G1 specifies token, Host allowlist, and TLS or SSH for LAN access, implying LAN exposure is supported; the plan binds only `127.0.0.1` and says the second user is supported "not [by] LAN exposure"; Deferred Decisions still lists "LAN policy for a second user".

**16. Major — "Classified log" is never defined.** Lines 164, 572. Repair uses "only the classified log" and the repair prompt receives "classified log plus typed facts", but the document never says who or what classifies, what categories exist, or what format is passed.

**17. Major — GitLab CE 19.2.5 is pinned while its version and retrievability are unresolved.** Lines 64, 349, 543. The plan fixes 19.2.5 as the vulnerable Omnibus version, but Open Questions asks whether that `.deb` is retrievable with a stable URL and hash, and Deferred Decisions still lists "GitLab Omnibus version and resource sizing".

**Nits.** (a) The validator bundle claims "no generator context" but includes the generated setup script, and prebuilt targets have no generated script (226, 621, 584). (b) Dirty Frag is "re-scoped" if its kernel is unavailable (544) but "becomes V1.1" if validation is unreliable (406), with no rule for which applies. (c) Terminology drifts: `target_id` versus `target_pack_id`, `authority: llm` versus `llm_assessed`, `pack_version`, and the field placement of `security_cleanup_failed` (204, 304-311, 87). (d) The typed-facts shape and the pre-run plan field lists are unspecified or inconsistent (291, 34 versus 484). (e) v2 vocabulary ("bank", "five CLI bank verbs", "immutable bank", "oracle", "scoring") is never defined (48, 382), and "corrected key" (517) and "currency display" (57) are unexplained leftovers. (f) "Manifest" is overloaded across evidence, attempt, pack, and bundle manifests (283, 306, 316, 622), and Ubuntu is given as both 24.04 and 24.04.4 (211-213).
