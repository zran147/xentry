# xentry V1 — Local CVE Reproduction with an LLM Agent and libvirt VMs

* **Author:** zran147
* **Date:** 2026-11-05
* **Status:** Brainstorm brief for `/egm-draft`

## Overview

xentry V1 is a local web application for one or two users. The user supplies a CVE link and a PoC link. The backend fetches both, extracts the facts, and runs a DeepSeek-backed Google ADK agent that writes a native setup script and a PoC driver. A runner-owned sequence creates a libvirt/KVM VM, runs the setup and PoC, collects evidence, invokes a separate, context-isolated LLM validator, and destroys the VM. The agent does not call `validate` or `destroy_vm`. The validator decides whether the run reproduced the vulnerability from the runner-collected evidence. SQLite stores CVE and job records; scripts, logs, and artifacts live on the filesystem. V1 is Linux-only and uses no container runtime in execution or deployment.

The reset from v2 is deliberate. V2 tried to build a general evidence-first pipeline and knowledge bank. It grew to roughly 12,000 lines across about 20 subsystems, produced three recipes it called verified, and could not be audited by its owner. V1 narrows the product to three known Linux targets and one local UI. It also changes the trust model: the VM, not a container, is the isolation boundary, and the success decision moves from the generated script to a runner-owned evidence probe plus a separate LLM validator with no generator context.

The cost of that change is that V1 still has a web attack surface, a long-running job runner, a libvirt harness, and an agent framework. It is smaller in features than v2 but not smaller in trust surface. The central question is not whether an agent can write a setup script. It is whether V1 can show that a validator pass was caused by the vulnerability and not by the agent, the PoC, the setup script, a leftover file, or a misconfigured target. V1 defers the full harness-owned oracle from v2. That deferral is acceptable only if the parts that prevent self-reported success remain: a runner-owned evidence probe, a nonce the actor cannot read, a null-actor check, evidence stored outside the agent's control, and an LLM validator that never shares context with the generator. V1 accepts that an independent LLM can still be fooled; the verdict is labeled `llm_assessed`, not deterministic. Without the nonce, null actor, and raw evidence, V1 repeats the old failure at a smaller scale.

This brief was produced from six review lenses: design, codebase details, zoom-out, comprehension, implementation readiness, and structural. The analysis is grouped by the risks that decide whether V1 is trustworthy, not by reviewer.

## Analysis

### 1. The validator is a separate LLM session, and self-reported success is still the risk (Blocker)

The old tree is still on disk at `/home/zran/ambitious_projects/xentry/`. Its evidence shows the exact failure V1 must not repeat. `/home/zran/ambitious_projects/xentry/var/work/CVE-2021-41773/50512/validation.json` contains only:

```json
{"ok": true, "errors": []}
```

`/home/zran/ambitious_projects/xentry/var/work/CVE-2021-41773/50512/verification.json` says `"status": "verified"`, `"attempts": 3`, `"successes": 3`, with no transcript hash, no nonce, no validator command, and no evidence pointer. That is a self-report with a success label. The old ADR 0006 at `/home/zran/ambitious_projects/xentry/docs/decisions/0006-one-poc-negative-control.md` openly says a PoC that only detects a version may pass false positives and that the negative control was deferred. ADR 0001 at `/home/zran/ambitious_projects/xentry/docs/decisions/0001-evidence-first.md` already states the right principle: the model extracts, plans, generates, and repairs, but never decides that a vulnerability is real and never executes code outside the sandbox. V1 should adopt that principle rather than rediscover it.

V1's decision is that the validator is a second DeepSeek session with fresh context: it does not see the generator's chat history, plan, repair history, or final summary. That removes the generator's own framing, but it does not make the validator deterministic. The same provider and model family can share prompt-injection failures, and an LLM can be persuaded by a setup script that manufactures the expected evidence. The owner accepts that risk for V1; the verdict must be labeled `llm_assessed` and the full harness contract remains the exit criterion.

V1 can defer the full oracle, the version-range probe, the fixed-build control, and the immutable bank. It cannot defer the runner-owned evidence path. The V1 contract is:

* The target pack defines a checked-in, fixed evidence probe keyed by a stable `target_id`: where the nonce goes, which command or HTTP request proves it, and what raw evidence to collect. The runner executes the probe, never the model. The independent LLM validator receives the raw evidence bundle and returns a structured verdict: `reproduced`, `not_reproduced`, or `inconclusive`, with a closed reason code and evidence references. It has no tools and cannot write evidence.
* The validator session runs outside the actor and is invoked by the runner, not by the generator. It has no VM, filesystem, network, or tool access. The generator cannot call `validate` and cannot see the validator's prompt or verdict before it is stored.
* The nonce is 128 bits, generated by the runner with `secrets.token_hex(16)` after provisioning, and placed where the actor has no direct read access. The setup script never sees it. A null actor run against the same probe must fail.
* The job status is a projection of the validation row written by the runner. The row stores the validator model, prompt hash, verdict, reason, evidence references, and an `authority: llm` marker. The agent's final message is stored separately and displayed as commentary. It is never the status.
* The record includes the target pack id and version, the validator model and prompt hash, the nonce id and placement, the request or command, the observed and expected values, the pre-run state, the null-actor result, and the evidence hash.

The three targets need fixed argv contracts so the runner and target pack, not the model, supply the proof material. For GitLab, the runner writes the nonce to a path readable by the GitLab service user but outside the document root, passes that path to the PoC, and parses the returned content. For PHP2Shell, the runner constructs the `--cmd` string, performs its own HTTP GET of the written file, and does not use the PoC's `--fetch` output as the pass condition. For Dirty Frag, the runner supplies a command that writes a root-only nonce from the escalated shell; the wrapper does not contain the proof. The LLM validator sees the raw evidence and the nonce, and judges whether the nonce appeared through the vulnerability.

There is a second trap the null actor does not close. A setup script runs as root inside the guest and can install a process that watches for the PoC's request and writes the expected file. The null actor never sends that request, so it would fail, but the malicious setup would still pass the real run without the vulnerability. The mitigations are a phase boundary and a one-time review of the bootstrap scripts: provisioning ends with a freeze, the nonce is generated after the freeze, mutate-capable tools are revoked, and the first three setup scripts are hand-reviewed for malicious content and hash-pinned for V1 acceptance. That review is a bootstrap safety check, not a human gate in the normal flow. After those three, the pipeline is fully autonomous: the LLM writes and repairs setup scripts from the evidence and classified logs. The accepted risk is explicit: a generated setup script can still react to the PoC, and an LLM validator can still be fooled. The nonce and null actor catch static and echoed markers, not a setup script written to fake the observed evidence. The independent validator is the remaining check, and it is LLM-assessed.

The validation record should also carry version and precondition evidence even though the full version probe is deferred: `uname -r` and the kernel package for Dirty Frag, `php -v` and the Apache module for PHP2Shell, and the GitLab version endpoint for GitLab. Without those, a pass on the wrong build looks identical to a pass on the right build. When the CVE link does not identify a vulnerable version, the job should fail with `version_unidentified` rather than guess.

### 2. The execution context is resolved: target VM, non-root actor (Blocker)

V1 uses the second option with hard rules:

* **No PoC code is built or executed on the host, ever.** The backend fetches and pins the public PoC artifact, hashes it, and copies it into the target VM. The VM builds it during an explicitly logged egress window. The build toolchains belong in the per-target base image: Go for the GitLab client, gcc and make for Dirty Frag, Python and `requests` for PHP2Shell.
* **The actor is a dedicated non-root user.** The PoC runs as `xentry`, not as the target service user and not as root. The nonce is readable only by the target service or by a root-only path that the vulnerability effect reaches. For PHP2Shell, the nonce must not be visible in `/proc/<pid>/cmdline` to the same uid; the runner writes it to a protected file and the RCE command reads it, or the target pack uses a mode-0600 file owned by the target service.
* **The validator runs outside the actor.** The runner collects the evidence, the independent LLM validator judges it, and the generator never sees the nonce or the validator prompt. The LLM validator has no tools.
* **The trade-off is recorded.** The actor shares the target VM's kernel and filesystem. For a web target, an actor running as the target service user could read the nonce without exploiting. A separate unprivileged user and a protected nonce make this workable, but it is weaker than a second VM. If a web target cannot be validated causally under this rule, a second minimal attacker VM is the fallback, and the one-VM assumption is revisited explicitly.
* **Dirty Frag runs in the target VM by definition.** The runner drives the PTY root shell and runs a root-only nonce proof from outside the actor. The VM is destroyed on every path because the page cache is contaminated.

The public PoC is the artifact under test. "The agent writes a PoC script" means "the agent writes a thin build and invocation wrapper around the pinned public PoC," not "the agent re-authors the exploit." The backend pins the commit, fetches a tarball or the selected files, hashes them, and copies them into the VM. The agent writes the wrapper. Re-authoring the exploit is a later capability, not V1.

For Dirty Frag specifically, the proof should not be "the PoC printed uid 0." The PoC patches `/usr/bin/su` in the page cache, so any probe that resolves `su`, `id`, or another PATH binary through the guest can report root without the exploit. The runner should drive the root shell and run a command that reads a root-only nonce, and it should record that the VM was fresh and the kernel matched. The VM is then destroyed from the host, on every path, because the page cache is contaminated.

### 3. The agent's tool trajectory is the job state machine (Blocker)

Five tools look narrow: `create_vm`, `run_setup_script`, `run_poc`, `validate`, `destroy_vm`. The parameters and the call order decide the real authority. If `create_vm` accepts libvirt XML, disk paths, network settings, or host device names, the agent can define a domain that mounts the host filesystem or joins the host network. If `run_setup_script` accepts a host path, the agent can run any file on the host. If `run_poc` accepts an arbitrary command, the agent has a host shell. If `validate` accepts an expected value, the agent can weaken the check. If the agent decides when to call `validate` and when to stop, the job sequence is a model output, not a state machine.

The stronger design is a runner-owned sequence: `queued -> creating -> provisioning -> ready -> running_poc -> validating -> succeeded | failed -> destroying -> done`. The runner calls create, freeze, inject the nonce, run the null actor, run the real actor, collect evidence, invoke the independent LLM validator, and destroy. The model is invoked at two declared points: extract typed facts from cited excerpts, and author or repair the setup script from typed facts plus a classified log, each under a step budget. `validate` and `destroy_vm` are not model-callable. If the five-tool interface is kept for the concept's sake, the tools are requests to the runner, the runner ignores out-of-order calls, and the runner still runs the validator unconditionally after the PoC. The validator is a separate session with no generator context and no tools; it cannot alter the evidence.

This is a reversal of the old tree's ADR 0007 at `/home/zran/ambitious_projects/xentry/docs/decisions/0007-llm-orchestration.md`, which explicitly chose an explicit Python state machine and said "do not give the model tools or filesystem/network access." V1 should either justify the reversal in a new ADR or drop the agent tool surface. The old tree also has an 80-line OpenAI-compatible DeepSeek client at `/home/zran/ambitious_projects/xentry/src/xentry/llm.py` and settings at `/home/zran/ambitious_projects/xentry/src/xentry/config.py` that already point at `https://api.deepseek.com`. LiteLLM and ADK add layers that the old code did not need.

Prompt injection is assumed to succeed at the text level. The fetched CVE page and PoC repository can contain instructions to ignore the prompt, exfiltrate the API key, or create a host mount. The controls are not "the model will resist." The controls are the tool schemas, the absence of host secrets in the guest, the VM boundary, the egress policy, and the runner-owned probe plus the independent LLM validator. A prompt-injection regression corpus should include a fake CVE page that asks for a host mount and a fake PoC that prints a success marker. The expected result is a failed job with a recorded reason, not a host effect.

### 4. The VM boundary is constrained: session libvirt first (Blocker)

`qemu:///system` is a privileged libvirt connection. A user in the `libvirt` group can define and start domains, attach host devices, and change network configuration. That is close to root on the host, and the QEMU process for a system domain runs as root, so a guest root shell becomes host file access. Working is not the same as least privilege. If the web app has no auth and is reachable from a browser, a malicious page could trigger a job that uses that authority.

V1 tests `qemu:///session` first. User-mode networking, local qcow2 overlays, and no host devices are enough for the three targets. If a target needs system libvirt, V1 uses a root-owned broker with a fixed verb set (`start_target(profile)`, `exec_in_guest(job, argv)`, `destroy(job)`) behind a Unix socket with peer credentials, and keeps the web app out of the `libvirt` group. Neither the generator nor the target chooses the connection URI. If system libvirt is kept, the risk acceptance is recorded: libvirt-group membership is root-equivalent.

The network claim also needs work. QEMU user-mode networking NATs guest traffic through the host. It does not automatically isolate the guest from the host LAN. The v2 brief had a provisioning proxy with an allowlist; V1 has no proxy. During provisioning, the guest needs package mirrors and source downloads. After provisioning, it should not reach the host LAN. V1 should enforce egress with host nftables rules per VM IP, `<forward mode='none'/>` after provisioning, or an nwfilter deny-by-default rule, with a logged build window. If that cannot be done with user-mode networking, use a bridge with nftables and accept the scope increase, or state the residual risk and test it. An egress test before the actor should fail closed. "The VM is the isolation boundary" is not true if the guest can reach the workstation's file server.

The device surface should be minimal: no host mounts, no 9p or virtiofs, no USB, no display or SPICE, no shared clipboard, no host devices. Use virtio disk, virtio net, and serial only. Bind every host forward to 127.0.0.1. Use transient domains, disable autostart, and destroy and undefine on every exit path. Keep QEMU and libvirt patched. A VM escape is still possible; the design should say so rather than claim the boundary is absolute.

For Dirty Frag, the destroy is a security control, not cleanup. A failed destroy is `security_cleanup_failed`, not a generic job failure. The destroy happens from the host through libvirt, never by running `su` or any guest command, and it happens on validation failure too.

The current workstation is WSL2. WSL2 forwards Windows localhost to WSL services, so "bind 127.0.0.1" does not mean only the WSL process can reach the app; a Windows browser or process can. WSL2 wall-clock time can also jump after a host suspend, so durations should be measured with a monotonic clock and wall-clock jumps should be logged. `/dev/kvm` must be present after a restart, and libvirtd must start without manual intervention. A job runner that depends on a daemon someone started by hand will fail the first time the machine reboots.

### 5. No-auth is only acceptable on loopback, and WSL2 loopback is not private (Major)

"No authentication" is defensible only if the app binds to 127.0.0.1 and the two users are two browsers on the same workstation. Even then, a malicious website can POST to `http://127.0.0.1:8000/jobs` from the user's browser. The attacker cannot read the response because of CORS, but the side effect is enough: create a VM, fetch an internal URL, run a job. CSRF protection is required. A startup-generated bearer token required on every mutation is the simplest control; it is a request-integrity token, not a user account. Add `SameSite=Strict` cookies, Origin and Host checks, and a Host allowlist for DNS rebinding. Requiring a JSON content type also prevents a cross-origin simple form POST.

If the second user is on another machine, no-auth on the LAN is a remote job-submission and URL-fetch endpoint. The minimum for LAN is the same token, a Host allowlist, and TLS or an SSH tunnel. "One or two users" is not a reason to skip the token; it is a reason the token can be a single shared secret. The brief should state which case V1 supports. If the two users are two Unix accounts on one host, localhost is not authentication either: any local user or process can drive VM creation and root-in-guest scripts. The Help screen should document the second-user path as SSH local port forwarding with the exact command.

The server fetches arbitrary URLs, which is an SSRF endpoint. Restrict schemes to http and https, resolve DNS and reject loopback, private, link-local, multicast, and cloud metadata addresses, re-check on every redirect, cap redirects at three, cap response size and time, send no cookies or auth headers, and log the resolved IP and the allow-or-deny decision. The fetched content is sent to DeepSeek, a third party; the UI should say so. The agent must not get a generic fetch tool, because that turns prompt injection into requests to internal services.

The UI must escape all log and PoC text, never render fetched HTML, and sanitize any Markdown from the model. Job ids should be UUIDs; file paths should be built by the backend, not from user input. The app runs as a non-root user, with the data directory at 0700 and secrets at 0600. No `shell=True` with model output. A restrictive Content Security Policy is cheap and should be on.

### 6. The job lifecycle and cleanup are a small distributed system (Major)

A GitLab Omnibus job can run for 20–40 minutes. A blocking HTTP request is not viable: the browser times out, the server worker is tied up, and a restart loses the job. V1 needs a job queue, a worker, a state machine, live progress, cancellation, and crash recovery. For one or two users this can still be one process with a background worker and a SQLite queue, but the states and the cleanup path must be explicit.

Suggested states: `queued`, `fetching`, `extracting`, `creating`, `provisioning`, `ready`, `running_poc`, `validating`, `succeeded`, `failed`, `cancelled`, `interrupted`. Every transition goes to an append-only event log. The UI reads the log and the job row. Server-sent events are the simplest live channel; polling is the fallback. A browser refresh must not cancel the job, and the live view must tail the persisted log, not an in-memory buffer.

Crash recovery is mandatory. Create the database row before creating the domain, and name the domain `xentry-<job_id>`. On startup, the worker lists libvirt domains whose names or metadata carry the xentry job prefix. Any domain without an active job is destroyed and undefined; its overlay and cloud-init ISO are removed. Any job in a running state is marked `interrupted` with a reason code and is never auto-resumed. A database-enforced single worker, not only `XENTRY_MAX_CONCURRENT_JOBS=1`, prevents two workers. `destroy_vm` is idempotent, and the job row records `destroyed_at`. A periodic sweep catches domains left by a killed process. The worker writes an intent event before each tool call or guest command and a result event after it, so the operation in flight when the process died is still visible.

Cancellation and the job timeout must both call destroy and write the reason code. Per-tool timeouts are separate from the job timeout. Retry policy is per target: setup retries get a fresh attempt directory and a new script hash; Dirty Frag retries get a fresh VM because the first attempt contaminates the page cache; no retry ever reuses a dirty guest.

The current `.env.example` defaults are not a budget: a two-hour job timeout, three setup attempts, three PoC attempts, 4 GB RAM, 2 vCPU, and 40 GB disk. A stuck job can hold the only VM slot for two hours. Three PoC attempts can run the same failed exploit three times. GitLab wants more than 4 GB. V1 should set per-target caps and record actual VM minutes and tokens: for example, one setup repair, one PoC re-run, 30 minutes for PHP, 60 for GitLab, 30 for Dirty Frag, a 50 GB disk ceiling, and a daily job cap. Retries are for transient fetch and LLM failures and for infrastructure failures, not for a failed exploit. Every timeout logs the in-flight tool, an argument hash, and whether cleanup ran.

### 7. SQLite for the tool-call log is the wrong shape (Major)

SQLite is a good index for job status, validator results, and CVE metadata. It is a poor store for the raw tool-call log. Command output, setup logs, and LLM transcripts are append-only, variable-size, and large. Putting them in rows bloats the database, makes `sqlite3` inspection painful, and couples log retention to schema migrations. The filesystem should hold one append-only JSONL log per job and one directory per job for scripts, artifacts, and captured evidence. The per-job attempt directory is authoritative; SQLite is a rebuildable index.

A minimal schema is enough. A small `cves` table is acceptable as a fetch cache, not as a knowledge bank; do not add bank features until a second job reuses a CVE. The core tables are:

* `jobs(id, cve_id, poc_url, target_id, state, created_by, created_at, started_at, finished_at, result, reason_code, image_sha256, attempt_dir, manifest_hash, agent_summary)`
* `tool_calls(id, job_id, seq, tool, params_json, params_sha256, started_at, finished_at, status, result_path, result_sha256)`
* `validations(id, job_id, target_pack_id, target_pack_version, validator_kind, validator_model, validator_prompt_hash, verdict, reason_code, evidence_json, evidence_sha256, null_actor_passed, nonce_id, ts)`
* `artifacts(id, job_id, kind, path, sha256, bytes)`
* `schema_version(version)` or `PRAGMA user_version`

Write the `tool_calls` row with status `running` before execution and update it after. A crash then leaves a visible incomplete call. Use WAL mode, foreign keys, a bounded busy timeout, and transactions for state transitions. Ship ordered, forward-only SQL migrations. Copy the database to `xentry.db.bak.<version>` before applying a migration, and refuse to start if the database version is newer than the code. Resolve the data directory to an absolute path at startup; `sqlite:///./var/xentry.db` changes meaning with the working directory. Use a fresh data directory and database name, and refuse to start if the directory contains a v2-shaped layout.

The audit trail must let a reader reconstruct a job without trusting the agent: the two input URLs and their fetched bytes with hashes, the redirect chain and resolved IP, the exact bytes or excerpts given to the model plus truncation offsets, the extracted facts, the model id and prompt version, every LLM request and response with token counts and the model id returned by the provider, every tool call with arguments and result, every guest command with transport, argv, user, stdout, stderr, exit code, timeout, and truncation, the VM id and libvirt state transitions, the validator request and evidence, the cleanup result, the config snapshot, the runtime fingerprint, and the cost. Failed jobs are retained; only bulky overlays and downloaded archives are pruned. No secret, API key, or guest password goes into the log or the guest. The redaction pass runs before any write and marks what it removed.

The UI should show the validator verdict, its `llm_assessed` authority label, and its evidence first, and the agent summary under a clear "agent commentary" label. The job status badge comes from the database row written by the backend, and a succeeded job must be impossible without a validation row that references that job's nonce. The downloadable job bundle should place validator evidence before the agent summary. What stays on disk: raw fetched bytes, full prompts and messages, full stdout and stderr, qemu and serial logs, every script version, and image paths. The UI shows hashes, sizes, and links; it does not render multi-megabyte logs inline.

### 8. The three targets are three harnesses, not three rows (Major)

The three targets differ in every expensive dimension:

* GitLab: a multi-GB Omnibus install, 4+ GB RAM, a long provisioning step, a service health check, and a version pin the concept does not name. The nonce file must be owned by the GitLab service user and unreadable by the actor.
* Dirty Frag: a pinned Ubuntu 24.04.4 kernel (6.17.0-23-generic), a reboot, a `uname -r` check, a C-compiled PoC, a PTY-driven root shell, and mandatory VM destruction because the page cache is contaminated.
* PHP2Shell: a source build of PHP 8.4.26 with Apache mod_php, configure flags and php.ini from the repository, a build toolchain, and a web-root nonce.

A single "target" abstraction that hides these differences will either be too thin to provision them or leak target-specific branches into the pipeline. The better shape is a target pack: a checked-in directory with a manifest and optional hand-written hooks. The manifest names the supported CVE ids, the base image and digest, resources, pinned kernel or packages, provision script, `reboot_required` as a first-class phase that survives the SSH drop, `disposable`, PoC acquisition (repository, commit, path, build commands, toolchain), the `poc_command` template with named slots, an optional `poc_driver` for interactive PoCs, the validator spec, per-phase timeouts, and a pack version. The generic pipeline reads the pack, runs the fixed probe, and invokes the independent validator session. No dynamic plugin loader in V1. The enforcement test is a dummy fourth pack that requires no edits outside its directory; if it touches the runner, the tool layer, or the schema, the contract failed.

The provisioning split should be explicit. The base image is pinned: OS, toolchains, and the driver. The target-specific setup script is what the LLM writes from the evidence. For the first three targets, that script is hand-reviewed once for malicious content and hash-pinned for V1 acceptance; after those, the normal flow is fully autonomous. The target pack declares whether provisioning is `prebuilt` (the first three) or `generated` (the normal flow). Record the image SHA-256, kernel release, package versions, and setup-script hash with every job. GitLab pins the Omnibus `.deb` version and URL plus SHA-256; if the CVE link does not identify the vulnerable version, fail with `version_unidentified` rather than guess. Dirty Frag pins the kernel package URL plus SHA-256, or uses a snapshot repository, and gates the run on `uname -r`. PHP builds PHP 8.4.26 once into the image with the transcribed configure flags and php.ini, not from the repo's Docker folder at runtime. A single global `XENTRY_VM_MEMORY_MB` cannot serve all three; resources belong in the pack.

All three can remain V1 acceptance targets, but the build order should be fixed: PHP2Shell first (smallest, no reboot, HTTP validator), GitLab second (same HTTP validator pattern, heavy provisioning), Dirty Frag third (kernel, reboot, PTY, mandatory destroy). The first target proves the pipeline; the second proves the pack generalizes; the third proves the hard case. If the schedule slips, Dirty Frag is the cut line. Do not cut the validator contract to save it.

The input contract must be honest. The user can paste an arbitrary CVE link, but V1 supports three CVEs. The backend should map the CVE id to a target pack and reject anything else with `unsupported_target` before any LLM spend or VM creation. The UI should list the supported set rather than imply general coverage. The arbitrary PoC link is similarly bounded: V1 accepts the pinned PoC for each target, or an alternate that matches the same invocation contract, and rejects the rest with `unsupported_poc`. If an unknown CVE is allowed at all, it should run in a clearly labeled research mode with no success claim and a low token cap, not in the normal pipeline.

The base-image question should be answered per target, not by a single image. One Ubuntu 24.04 cloud image plus target provisioning may cover PHP2Shell and GitLab. Dirty Frag needs the pinned kernel; install it from a package stored at image-build time and assert `uname -r` after reboot, rather than fetching a kernel at job time and risking a newer one. A small image catalog with hashes and a disk ceiling is simpler than forcing one image.

### 9. The UI has no honest vocabulary for state, verdict, or evidence (Major)

The concept says the LLM may summarize but must not be the authority. The UI is where that rule either holds or fails. The current design has one job status and no separate verdict, no pre-run plan, and no screen state for a validator that could not run. "Succeeded" would then mean "the pipeline finished," which a user will read as "the exploit worked." The comprehension lens found four concrete failures:

* "Target" means the lab VM, the vulnerable service, and the PoC's `-u` argument. The user cannot tell which image, version, validator, and resource footprint will be used before committing an hour.
* A job can complete while the PoC failed, or the validator can error while the agent's prose says "successfully exploited." There is no defined screen state for disagreement.
* `validate` and `destroy_vm` appear as agent steps, so the UI timeline implies the model owns the check and the cleanup.
* Cancellation, orphan cleanup, and Dirty Frag's mandatory destroy have no user-facing contract.

The UI needs three fields everywhere: job state (`queued`, `running`, `validating`, `completed`, `failed`, `cancelled`, `interrupted`), verdict (`reproduced`, `not reproduced`, `inconclusive`, `not run`), and verdict authority (`llm_assessed` in V1; deterministic in the later harness contract). The verdict is written by the runner from the validator session's structured output only. Ban "succeeded" and "verified" from the UI. The agent summary is a separate panel labeled "Agent summary — not authoritative." When the summary and the verdict disagree, a fixed banner says the validator controls the verdict. Each target carries fixed "What this proves / what this does not prove" text written by the project, not generated per run; for V1 the "does not prove" text says an independent LLM assessed the evidence and can be fooled.

Before a job starts, a plan panel should show the canonical CVE id, the matched target pack or an explicit "no supported target pack for this CVE in V1," the lab VM image and kernel, RAM and disk, the fixed probe and the validator session, and the time and token caps. "Start job" confirms that plan. A "Check links" action should fetch both URLs and show HTTP status, content type, bytes, extracted text size, the detected CVE id, the detected repository or code file, and explicit warnings such as "repository landing page; code files were not fetched," "text truncated at N tokens," or "no CVE id found." Show the exact extracted text that will be sent to the model, escaped and plain, with a SHA-256 and a download link. Never render fetched HTML or remote images. Provide a paste-text fallback when a fetch fails.

The live view should be a stage timeline (Fetch, Extract, Plan, Create VM, Provision, Run PoC, Validate, Destroy, Report) with the current stage, elapsed time, and per-stage status. No invented percentage. Logs are tagged by source (agent, VM console, setup, validator, system), filterable, with exact commands, exit codes, durations, truncated output, and a full-log link. A quiet stage shows a stall notice with Cancel offered. Each job has a stable URL with SSE reconnect and backfill. The tab title changes on terminal state, and the log remains available after the job ends.

Every failure should render as one sentence, one primary action, and a "Technical details" disclosure. The failure classes are closed: source fetch, unsupported CVE, provider or auth, VM creation, provisioning, target health, PoC assertion, validator error, timeout, budget exhaustion, cancellation, interruption, and teardown failure. Retry creates a fresh job with a fresh fetch and a fresh cost, linked to the original; it does not resume.

A System screen should run preflight checks: libvirt connect, version, and domain list; KVM present; free RAM and disk against per-target estimates; base image and required kernel; DeepSeek reachability and auth; database writable; bind mode and reachability. Block or warn on Start when a check fails, naming the failed check. Show per-target estimates and the actual caps. Do not display currency unless the pricing table is versioned and dated; token counts are always truthful. An orphan banner on startup lists xentry-managed domains and offers a single destroy action. Dirty Frag has no "leave VM running" action, and its result states that the VM was destroyed.

Four screens and one help modal are enough: New Job, Jobs, Job Detail, System, and Help. No dashboard, no settings editor for every environment variable, and no single-page app. The terms need one meaning each: "lab VM" and "vulnerable service" instead of an overloaded "target"; "evidence" means the validator record, not the agent's prose; "native" is an implementation constraint, not a user-facing promise.

### 10. HTML is the wrong ingestion format for both inputs (Major)

A CVE link is often NVD, cve.org, a GitHub advisory, or a vendor page. Many of those render with JavaScript or put the useful data in a JSON API. A PoC link is usually a GitHub repository; the HTML page gives the README and file list, not the source code the agent needs to build and invoke the PoC. Sending the HTML of both pages to the model will produce thin or wrong facts, and it burns context on navigation and scripts.

V1 should detect the source shape and use the cheapest reliable representation:

* NVD: the CVE API JSON.
* cve.org: the CVE JSON record or the API.
* GitHub advisory: the advisory API or the rendered page.
* GitHub repository: resolve the default-branch commit through the API, fetch the README and the small text files the README names, and fetch the repository tarball at that commit. Hash every artifact.
* Generic page: HTML-to-text with script and style removal, a byte cap, and a token cap.

The model should receive a bounded evidence bundle with source URLs, hashes, and quoted excerpts, not raw HTML. Fetch with a byte cap (for example 256 KB), a content-type check, a timeout, and a redirect cap; cap the extracted text at roughly 20k tokens. This reduces prompt-injection surface and token cost, though it does not eliminate injection. A `fetch_url` tool for the agent would add SSRF and injection surface; do not add it in V1. If the evidence bundle is insufficient, the job fails with `evidence_insufficient` and the user can supply a better link.

The PoC artifact should be pinned by commit or hash and copied into the VM. The agent should not clone an arbitrary repository at run time; that makes the run non-reproducible and lets a repository change under the test. The backend fetches, hashes, and stores it; the VM builds it. The public PoC is untrusted code, but it runs only in the VM. The PHP configure flags and php.ini should be transcribed into a checked-in build file, not read from the repo at runtime.

The stronger prompt-injection control is a two-stage model use. A tool-less extractor reads cited excerpts and returns typed facts. A generator sees only typed facts and the target pack, not raw fetched HTML, and has no fetch or execute tools. Per-target prompt modules keep one target's hints from regressing another. This is more code than one prompt, but it puts the untrusted text in a context that cannot call tools.

### 11. ADK is the most replaceable component and the least proven (Major)

The agent loop is five tools and a mostly linear pipeline. Google ADK brings a session and event model, tool abstractions, and a dependency tree designed around Gemini. DeepSeek through LiteLLM may work, but tool-calling behavior (schema adherence, parallel calls, malformed arguments, retries) is not proven for this combination. The concept limits ADK to LLM and tool orchestration, which is the right constraint, but that is still a framework in the trust path. A failed tool call has to be attributed across ADK's schema and session model, LiteLLM's translation, and DeepSeek's function-calling behavior, and each layer can change independently.

Run a one-week spike before committing: ADK plus LiteLLM plus `deepseek/deepseek-chat`, two tools, a fake VM backend, and 20 scripted scenarios including malformed tool arguments and a prompt-injection page. Measure valid tool-call rate, loop count, token use, and recovery from a tool error. If the rate is poor, fall back to a direct LiteLLM function-calling loop of roughly 150–250 lines. Put ADK behind a small `AgentRuntime` or `ModelAdapter` interface so the fallback is a swap, not a rewrite. Cap iterations and tool calls; log the raw serialized request and response at the LiteLLM layer, not from ADK's internal events. Disable or map ADK's internal retries to the job retry policy so a tool is not re-executed without a new log row. No sub-agents, no long-term memory, no ADK web UI. Record the concrete model id returned by the provider, because `deepseek-chat` is an alias that can move. The validator session is a direct LiteLLM call, not an ADK agent: fixed system prompt, no tools, no session history, and no shared state with the generator.

There is a deeper alternative: a deterministic pipeline with LLM calls at fixed steps (extract facts, write setup script, write PoC driver, summarize) is more reproducible and easier to audit than an agent that chooses the next tool. The old tree's ADR 0007 chose exactly that, and its 80-line client already speaks the DeepSeek OpenAI-compatible API. LiteLLM buys a model-name mapping, not capability. The concept chooses an agent, so V1 should test whether the agent adds value over the pipeline. If it does not, the agent is ceremony.

### 12. The implementation still leaves load-bearing seams open (Major)

The concept describes behavior, not interfaces. Several seams must be decided before the first target is coded, because changing them later touches the validator, the tool adapters, and the state machine at once.

* **Guest transport.** libvirt has no portable exec channel. Choose SSH with a per-job key injected by cloud-init, or qemu-guest-agent if it is present in every image. Define the command log schema: transport, argv, user, stdout and stderr paths, exit code, timeout, and truncation. SSH is the simpler default; the guest agent is a fallback if SSH cannot survive a reboot cleanly.
* **VM driver interface.** Define `VmDriver` with `create(profile)`, `exec(user, argv, tty)`, `copy_in`, `copy_out`, `reboot`, `destroy`, and `get_ip`. Implement `LibvirtDriver` for real use and `FakeDriver` for tests. Gate the fake driver behind an explicit test setting and refuse to run a production job with it.
* **Guest exec and HTTP probe interfaces.** Target-pack probes should use narrow `GuestExec` and `HttpProbe` interfaces, so each probe can be tested against a canned transcript and a local HTTP server. A probe must not import the provisioner or share mutable state with it.
* **Reboot phase.** Dirty Frag needs a `reboot_required` phase that survives the SSH drop, waits for the guest to return, and checks `uname -r`. A `run_setup_script(reboot=true)` semantic or a separate `reboot_vm` step is enough; the agent cannot express this with a plain script call.
* **Tool and route signatures.** `create_vm(profile_id)`, `run_setup_script(job_id, script_name)`, `run_poc(job_id, args)`, `destroy_vm(job_id)`. The model never passes XML, host paths, image URLs, or arbitrary commands. Script bytes are persisted, hashed, and logged before execution. The validator is not a tool; the runner invokes `assess(evidence_bundle) -> LlmVerdict` after evidence collection, and the generator cannot see or call it.
* **Base-image strategy.** For the first three targets, prebuild one image per target, or one base plus a pinned kernel package for Dirty Frag. After the golden set, the normal flow may use a generic pinned image and a generated setup script. The target pack declares `provisioning: prebuilt` or `provisioning: generated`. Store the image digest, kernel release, package versions, and setup-script hash. A job-time `apt install` against an unpinned mirror is a drift risk; pin the package or snapshot.
* **Config and paths.** Resolve the data directory to an absolute path. Reject a relative SQLite URL. Keep `.env` at 0600. Per-target resources belong in the pack, not in global environment variables. Use a fresh data directory and database name for V1, and refuse to start against a v2-shaped layout.
* **Rollout and rollback.** V1 runs from a local virtual environment and a systemd unit; no Docker. To upgrade, stop the worker, back up the database, apply forward-only migrations, and restart. In-flight jobs are marked `interrupted` and their VMs are destroyed. A schema version newer than the code refuses to start. A rollback restores the database backup and the previous code. Do not migrate while a job is running.
* **Testability.** The fake driver, validator fixtures, a scripted model client, a prompt-injection corpus, and a kill-and-restart test are part of V1, not a later hardening phase. Without them, every test needs KVM and the harness bugs survive.

The implementation-readiness lens is blunt about timing: the validator contract, the PoC locus, the VM parameter boundary, the fetch contract, the image strategy, the reboot phase, the state machine, the schema, the web controls, and the driver interfaces must be decided before coding. Authentication, a second VM, concurrency, the full oracle, the bank, and a second source can wait, but the records they would need must be written now.

### 13. The concept has no definition of done (Major)

"An independent validator decides success" is a mechanism, not an acceptance test. V1 needs a small set of falsifiable criteria:

* Each of the three targets passes its runner-owned probe and independent LLM validator on two consecutive clean runs from a fresh VM, with the evidence stored and the verdict labeled `llm_assessed`.
* The null actor fails for each target probe, and no succeeded job exists without a validation row for that job's nonce.
* A prompt-injection fixture (a fake CVE page that asks for a host mount, and a fake PoC that prints a success marker) produces a failed job and no host effect.
* Killing the worker mid-job leaves no running domain and no stale overlay after restart; the job is marked `interrupted`.
* Every tool call and guest command is visible in the UI and persisted in the log; a downloadable bundle reconstructs the job.
* A failed job reports a closed reason code and a next action; a succeeded job shows the validator evidence, not just the agent summary.
* The UI never uses "succeeded" or "verified"; it shows job state and verdict separately, and the agent summary is subordinate.
* A pre-run plan shows the target, image, version, validator, and caps before the job starts, and "Check links" shows what was fetched and what was truncated.
* No job exceeds its VM-minute, token, or disk cap; the actuals are recorded.
* The app binds to loopback; the mutation token, CSRF, Host, and Origin checks are on; the SSRF guard rejects a private address.
* A dummy fourth target pack with `provisioning: generated` requires no edits outside its directory and no human review.
* The ADK spike meets its tool-call threshold, or the direct LiteLLM fallback is in use.
* An upgrade with a schema change preserves the old database backup, marks in-flight jobs interrupted, and leaves no orphan VM.

Without criteria like these, V1 can ship a demo that works once and a UI that says "success" because the model said so.

### 14. The prior failure modes are only partly addressed, and the old tree has reusable parts

| Prior failure | V1 control | Gap |
| --- | --- | --- |
| Self-reported success | runner-owned probe, independent LLM validator, nonce, null actor | the LLM validator can be fooled; the setup script can react to the PoC; this is an accepted V1 risk |
| Unbounded scope | three targets, local UI, no bank | web app plus ADK plus three harnesses is still broad |
| Weak Docker isolation | VM boundary, no containers | `qemu:///system` authority and guest egress are unresolved |
| No audit trail | SQLite plus filesystem logs | no event schema, no redaction contract, logs may land in SQLite |
| Agent trajectory as state machine | runner-owned sequence in this brief | the concept still lists `validate` and `destroy_vm` as model tools; the validator is now a runner step |
| No honest UI state | state, verdict, and authority in this brief | the concept has one status field and no disagreement state |

The old tree is not all waste. `/home/zran/ambitious_projects/xentry/src/xentry/llm.py` is an 80-line DeepSeek-compatible client; `/home/zran/ambitious_projects/xentry/src/xentry/evidence/store.py` is a 113-line content-addressed store; the recipe directories under `/home/zran/ambitious_projects/xentry/var/work/` are usable as fixtures and prompt examples; `/home/zran/ambitious_projects/xentry/docs/vm-builder.md` records known failures (Struts curl exit 18, cache/device-graph mismatch, PHP version drift). The old evidence store's `store_url` follows redirects without an SSRF check, so reuse the content-addressed shape, not the fetch code. The old recipes' `verification.json` files are self-reported, so use them as environment fixtures and prompt examples, not as proof. The old ADRs are a record of choices that were later reversed: Docker first, Postgres/S3/Temporal, boxes reuse, human approval, no agent tools. V1 should record which reversals are intentional and why, rather than silently contradicting them.

### 15. Host and operational assumptions

The current workstation is WSL2. The concept says `qemu:///system` is verified working, but five operational checks still matter: `/dev/kvm` must be present after a restart, libvirtd must start without manual intervention, WSL2 localhost forwarding must be understood as part of the web exposure, wall-clock jumps after suspend must not corrupt durations, and a 4+ GB GitLab guest must fit the host's memory alongside the web app. If WSL2 cannot provide stable nested KVM, the host assumption is wrong and the harness has no fallback. That should be tested in the first spike, not discovered during the first GitLab run.

## Goals vs. Non-Goals

### In-scope goals

* **G1. Local operation.** The app binds to 127.0.0.1 by default. One or two users on the same workstation use it without accounts. Every mutation requires a startup-generated request-integrity token, and LAN access, if enabled, requires the same token, a Host allowlist, and TLS or an SSH tunnel.
* **G2. Bounded input.** The app accepts a CVE link and a PoC link, detects the source shape, fetches a bounded evidence bundle, stores the raw bytes and hashes, and rejects unsupported sources, CVEs, and PoCs with a reason code before spending a VM.
* **G3. Runner-owned pipeline.** The runner owns the sequence: create, provision, freeze, run, validate, destroy. The model is invoked at two declared points, extraction and setup authoring or repair, and has no fetch or execute tools. After the three hand-reviewed bootstrap scripts, setup authoring and repair are fully autonomous; no human gate remains in the normal flow. If ADK is kept, it sits behind an `AgentRuntime` interface and does not own the sequence.
* **G4. VM harness.** libvirt/KVM runs one VM at a time. The domain XML comes from a fixed template. There are no host mounts, host devices, shared folders, or display devices. Each job gets a fresh overlay and cloud-init ISO, and both are removed after the job. Port forwards bind to 127.0.0.1.
* **G5. Target packs.** Each of the three targets has a checked-in pack: base image, resources, pinned versions, actor user, setup inputs, PoC artifact and commit, validator probe spec, expected evidence, and destroy policy. A dummy fourth pack must require no pipeline edits.
* **G6. Runner-owned evidence and independent LLM verdict.** Each target pack defines a checked-in, fixed evidence probe and nonce placement. The runner executes it outside the actor. Each run uses a fresh 128-bit nonce generated after provisioning, and a null actor must fail. A separate DeepSeek session with no generator context and no tools receives the raw evidence and returns a structured verdict. The verdict is labeled `llm_assessed`; V1 accepts that an LLM can be fooled. The job status is a projection of the validation row; the agent summary is commentary.
* **G7. Execution isolation.** All untrusted PoC code is built and run inside the target VM as a dedicated non-root actor. Nothing from the model or the PoC executes on the host. No container runtime is used in xentry or in target provisioning. A second attacker VM is considered only if same-VM validation cannot be made causal, and that is an explicit scope decision.
* **G8. Job lifecycle.** Jobs are asynchronous, queued, cancellable, and recoverable. The UI shows state and live logs over SSE with a polling fallback. A startup sweep removes orphan domains, overlays, and ISOs. Transient domains and a single VM slot are enforced by code and the database, not only by configuration.
* **G9. Storage and audit.** The per-job attempt directory and append-only JSONL logs are authoritative. SQLite indexes jobs, tool calls, validations, and artifacts. Failed jobs are retained. Secrets are redacted before write. A downloaded bundle reconstructs the job.
* **G10. Security baseline.** Request-integrity token, CSRF, Host, and Origin checks are on. The SSRF guard rejects private and loopback addresses on every redirect and logs the decision. Logs are escaped. The guest never receives host secrets. QEMU uses a minimal device set. Guest egress is restricted or the residual risk is documented and tested.
* **G11. Budgets and failure codes.** Per-target time, memory, disk, and token caps are enforced by the runner. Retries are limited to transient and infrastructure failures. Every failure has a closed reason code and a next action.
* **G12. Testability.** A fake VM driver covers the job lifecycle without KVM. Validator fixtures cover pass and fail. A prompt-injection corpus and a null-actor test are part of the suite. A kill-and-restart test covers cleanup.
* **G13. Honest UI.** Job state, verdict, and verdict authority are separate fields. "Succeeded" and "verified" are banned from the UI. A pre-run plan and a link check show what will run before it runs. The agent summary is subordinate to the validator evidence, and the V1 verdict is visibly labeled `llm_assessed`. Four screens and one help modal are enough.
* **G14. Operational readiness.** The app runs from a local virtual environment and a systemd unit, with no Docker. The database has a schema version, a backup before migration, and a documented rollback. An upgrade marks in-flight jobs interrupted and destroys their VMs.

### Out-of-scope non-goals

* User accounts, roles, multi-tenancy, or remote access without a token.
* General CVE coverage. V1 supports the three named CVEs and rejects others before provisioning.
* Arbitrary PoC adaptation. V1 runs the pinned PoC or an alternate that matches the same invocation contract.
* Windows, macOS, browser, GPU, hardware, cloud-only, or network-callback targets.
* Docker or any container runtime in xentry or in target provisioning.
* Concurrent VMs, a second attacker VM by default, multi-VM topologies, high availability, or cloud deployment.
* The full v2 contract: deterministic human-authored validators, harness-owned version-range probes, fixed-build negative controls, immutable bank versions, scoring, multiple advisory and PoC sources, and the five CLI bank verbs. V1 uses a context-isolated LLM validator and accepts the false-positive risk.
* Automatic publication or export of results, and the license gate that would come with it.
* A general agent platform: ADK sub-agents, long-term memory, the ADK web UI, or model-driven tool selection beyond the declared points.
* Proving real-world exploitability or safety. V1 records a lab reproduction, not a production risk assessment.
* A polished single-page app, mobile support, a frontend build chain, a dashboard, or a settings editor for every environment variable.
* Unlimited retries, indefinite artifact retention, or a disk budget beyond the stated ceiling.
* Automatic re-authoring of the exploit for V1.
* A human approval gate for generated setup scripts in the normal flow. Only the first three bootstrap scripts receive a one-time malicious-content review; the normal flow is autonomous.
* Dynamic target packs or a plugin loader.
* Currency display without a versioned and dated pricing table.

### Success criteria

* All three targets pass their runner-owned probe and independent LLM validator on two consecutive clean runs from a fresh VM, with evidence stored, the verdict labeled `llm_assessed`, and status written by the backend.
* The null actor fails for each target probe, and no succeeded job lacks a validation row tied to its nonce.
* The prompt-injection fixture produces a failed job and no host effect.
* Killing the worker mid-job leaves no running domain and no stale overlay after restart.
* Every tool call and guest command is visible in the UI and persisted in the log; a job bundle reconstructs the run.
* A failed job reports a closed reason code and a next action.
* The UI shows job state, verdict, and verdict authority separately, never uses "succeeded" or "verified," and keeps the agent summary subordinate.
* A pre-run plan shows the target, image, version, validator probe, and caps; "Check links" shows what was fetched and what was truncated.
* No job exceeds its caps; VM minutes and tokens are recorded.
* The app binds to loopback, the mutation token and CSRF checks are on, and the SSRF guard rejects a private address.
* A dummy fourth target pack with `provisioning: generated` requires no edits outside its directory and no human review.
* The ADK spike meets its tool-call threshold, or the direct LiteLLM fallback is in use.
* An upgrade with a schema change preserves the old database backup, marks in-flight jobs interrupted, and leaves no orphan VM.

## Alternatives Weighed

1. **Runner-owned sequence versus agent-owned tool trajectory versus a fully deterministic pipeline.** Rejected: the agent-owned trajectory, because it makes the job state a model output and hands the model a success verb. Rejected: a fully deterministic pipeline that removes the agent the concept asks for. Chosen: runner-owned sequence with the model at two declared points, plus the deterministic pipeline as the comparison baseline. Revisit if the agent adds no value over fixed steps.
2. **One VM with a target-side actor versus host execution versus a second attacker VM.** Rejected: host execution (untrusted code on the workstation) and a second VM as the default (breaks the one-VM assumption and doubles cost). Chosen: target-side non-root actor, validator outside the actor, fresh nonce, frozen setup. A second minimal attacker VM is the fallback if same-VM validation cannot be made causal. Revisit if a web target fails the causality test.
3. **Independent LLM validator versus human-authored deterministic validators versus the full v2 oracle.** Rejected for V1: human-authored deterministic validators (the owner chose the independent-session approach) and the full v2 oracle (scope and schedule). Chosen: a checked-in target-pack probe with a fresh nonce and null actor, plus a separate DeepSeek validator session with no generator context and no tools. The verdict is labeled `llm_assessed` because it is not deterministic. Revisit when the harness contract lands; then the validator interface stays and the implementation becomes deterministic.
4. **Five agent tools versus a reduced model surface.** Rejected: `validate` and `destroy_vm` as model-callable tools, because they let the model choose the decision and the teardown. Chosen: create, provision, run, validate, and destroy are runner steps; the model gets extraction and setup authoring or repair. If the five-tool shape is kept for the concept, the tools are requests and the runner enforces the order. Revisit if the agent needs a capability the runner cannot expose safely.
5. **Frozen target fixtures versus per-run generated setup scripts.** Rejected: regenerating the first three targets' setup on every run, because the environment under test moves and a reactive setup can fake the oracle. Chosen: hand-reviewed, hash-pinned setup scripts for the first three only, as a one-time malicious-content check; after those, the normal flow is fully autonomous and the LLM generates and repairs setup scripts. Revisit if a generated setup script is found to manufacture evidence; the independent validator and null actor are the controls.
6. **Web UI first versus an engine with a thin UI versus a CLI only.** Rejected: a UI-first build with the engine inside request handlers, and a CLI-only product that ignores the stated requirement. Chosen: an engine with a programmatic interface first, then a thin server-rendered UI and an SSE endpoint. The UI is an adapter, not the core. Revisit if the UI work dominates the schedule.
7. **All three targets versus one vertical slice.** Rejected: cutting to one target in the product scope. Chosen: all three remain V1 acceptance targets, but the build order is PHP2Shell, GitLab, then Dirty Frag, and the pipeline gate is the first target. Revisit if Dirty Frag's PTY validation or kernel pin cannot be observed reliably; it becomes V1.1, not a reason to weaken the validator.
8. **`qemu:///session` versus `qemu:///system`.** Rejected: system by default, because a libvirt-group user is close to root on the host and the system QEMU process runs as root. Chosen: test session first; use system only if a target requires it, with a root-owned broker, a dedicated user, a loopback-only app, and a fixed domain template. Revisit if session cannot provide user-mode networking or KVM access on the host.
9. **Source-aware ingestion versus HTML-only.** Rejected: HTML-only, because CVE pages are JavaScript-heavy and PoC links are repositories, not articles. Chosen: JSON APIs where they exist, GitHub raw files or a pinned tarball, and HTML-to-text as a fallback. Revisit if a source has no usable API and the HTML fallback is good enough.
10. **Filesystem attempt directories plus a SQLite index versus SQLite for everything versus no database.** Rejected: SQLite for command output and LLM transcripts, and a knowledge-bank-style `cves` table before it is needed. Chosen: append-only JSONL and per-job directories as the source of truth, with a minimal SQLite index that can be rebuilt. Revisit if the job list outgrows the index or a second consumer appears.
11. **Asynchronous queue versus blocking request.** Rejected: blocking, because jobs run for tens of minutes and must survive a browser refresh. Chosen: a SQLite-backed queue with one worker, SSE, cancellation, and startup recovery.
12. **One process with a background worker versus separate web and worker processes.** Rejected for V1: a separate worker with a message broker or a daemon supervisor adds operational surface. Chosen: one process with a background worker and a durable claim; if restart robustness proves insufficient, split the worker and keep SQLite as the queue.
13. **One base image versus a small per-target image catalog.** Rejected: forcing one image when Dirty Frag needs a pinned kernel and GitLab needs more disk and RAM. Chosen: one Ubuntu 24.04 base where it works, plus a pinned-kernel image or a kernel package stored at image-build time for Dirty Frag. Each image is hash-pinned and disk-capped.
14. **Pinned public PoC plus a wrapper versus the agent re-authoring the exploit.** Rejected: re-authoring for V1. It adds a second source of error, weakens the link to the linked PoC, and turns the agent into an exploit developer. Chosen: pin the commit, hash the artifact, build it in the VM, and let the agent write the setup script and the invocation wrapper. Revisit if a public PoC cannot be built or invoked.
15. **No auth on loopback versus a request-integrity token versus full accounts.** Rejected: no token on loopback (CSRF and WSL2 localhost forwarding) and full accounts for two users. Chosen: no user accounts, a startup-generated token on mutations, and a Host allowlist. Revisit if a third user or a remote consumer appears.
16. **ADK plus LiteLLM versus a direct LiteLLM loop versus the old 80-line HTTPX client.** Rejected for now: a direct loop without a spike, and an unexamined return to the old client. Chosen: a one-week ADK spike behind an interface, with the direct LiteLLM loop as the fallback and the old client as evidence that the provider call is small. Revisit if the spike shows poor tool-call reliability or if the runner-owned sequence needs no agent.
17. **Ground-up code versus reuse of the old tree.** Rejected: importing the 12,000-line tree or its Postgres/Alembic stack. Chosen: ground-up code, with the old LLM client, evidence store, recipe fixtures, failure notes, and ADRs as references. Revisit if the libvirt harness exceeds its schedule; the old QEMU code is a reference, not a dependency.
18. **Fresh nonce and null actor now versus deferring all verification work.** Rejected: deferring everything, because the old failure returns immediately. Chosen: keep the runner-owned probe, the nonce, and the null actor in V1, add an independent LLM validator, and defer the deterministic version-range probe, fixed-build control, and immutable bank. Revisit when the end-to-end path is stable; add the deferred checks without changing the validator interface.
19. **One status field versus separate job state and verdict.** Rejected: one field, because "finished" and "reproduced" are different claims and the model's summary would fill the gap. Chosen: job state plus verdict, with the verdict written only by the harness. Revisit never for the UI; a single summary field may exist only alongside both.
20. **Blind submit versus a pre-run plan and link check.** Rejected: accepting two URLs and discovering the target, version, truncation, and validator after an hour. Chosen: a plan panel and a Check links step that show what will run and what was fetched before Start. Revisit if the extra step slows the one or two users enough to matter; it is still cheaper than a wasted VM.
21. **Ad hoc schema versus versioned migrations from the first commit.** Rejected: creating columns as needed, because the first added column breaks existing databases and the audit log is the product. Chosen: a schema version, forward-only migrations, a backup before migration, and a refusal to start on a newer database. Revisit never; the cost is small now and large later.
22. **Second LLM session versus same-session self-check.** Rejected: same-session self-check, because the generator's context and framing carry over and the check is not independent. Chosen: a second DeepSeek session with a fixed prompt, no generator history, no tools, and raw evidence only. The residual risk is correlated model failure and prompt injection; the verdict is labeled `llm_assessed`.

## Key Decisions & Staging for Next Steps

### Decisions carried into the draft

* The runner owns the sequence and the job status. The model is invoked at extraction and setup authoring or repair. `validate` and `destroy_vm` are not model-callable; if the five-tool shape is kept, the tools are requests and the runner enforces order and parameters.
* The validator is a separate DeepSeek session with fresh context, no generator history, no tools, and raw runner-collected evidence. The target pack defines the fixed probe and nonce placement; the runner executes it. The verdict is stored with `authority: llm` and labeled `llm_assessed`. V1 accepts that an LLM can be fooled; the full harness contract replaces this validator later.
* The first three targets use hand-reviewed, hash-pinned setup images and scripts for V1 acceptance. The review is a one-time malicious-content check, not a human-in-the-loop in the normal flow. After those three, the pipeline is fully autonomous: the LLM generates the setup script from the evidence and repairs it from classified logs. The accepted risk is that a generated setup script can still react to the PoC; the nonce and null actor do not close that hole, and the independent validator is LLM-assessed.
* All untrusted PoC code is fetched and pinned on the host, copied into the target VM, built there, and run as a dedicated non-root actor. Nothing from the model or the PoC is built or run on the host. A second attacker VM is the fallback if same-VM validation cannot be made causal.
* The five tools have backend-owned schemas and fixed parameters. No libvirt XML, host paths, arbitrary commands, or expected values come from the agent.
* The app binds to 127.0.0.1 by default. Every mutation requires a startup-generated token. CSRF, Host, and Origin checks are on. The SSRF guard rejects private addresses on every redirect. LAN access requires the token, a Host allowlist, and TLS or an SSH tunnel.
* Jobs are asynchronous and queued. One worker, one VM at a time, enforced by the database. The UI uses SSE with a polling fallback. Cancellation and startup cleanup are part of V1. Domains are transient, port forwards bind to loopback, and destroy is idempotent.
* The per-job attempt directory and append-only JSONL logs are authoritative. SQLite is a rebuildable index. Failed jobs are retained. Secrets are redacted. The agent summary is separate from the validator verdict.
* The target pack is the boundary for target-specific knowledge. The generic pipeline does not branch on GitLab, Dirty Frag, or PHP2Shell. A dummy fourth pack must require no pipeline edits.
* The input registry rejects unsupported CVEs and PoCs before LLM spend or VM creation. The UI lists the supported set.
* Ingestion is source-aware. The PoC artifact is pinned by commit or hash. The model sees a bounded evidence bundle with citations, and untrusted text never enters a tool-capable context.
* ADK sits behind an `AgentRuntime` interface. The one-week spike must meet a tool-call threshold or the direct LiteLLM loop is used. The runner-owned sequence is the control plane in either case.
* Job state and verdict are separate UI fields. "Succeeded" and "verified" are banned from the UI. The agent summary is labeled non-authoritative. A pre-run plan and a link check are part of the job flow. Four screens and one help modal are enough.
* `VmDriver`, `GuestExec`, `HttpProbe`, and `LlmVerdict` are defined before the first target is coded. The fake driver and validator fixtures are part of V1, not a later test phase.
* The database has a schema version, forward-only migrations, a backup before migration, and a documented rollback. The data directory is absolute. A v2-shaped data directory is refused.
* The v2 failure taxonomy, actor/oracle lesson, null-actor idea, and attempt-ledger idea are carried forward. The v2 code, schema, and Postgres/Alembic stack are not.

### Decisions still open

* **Session versus system libvirt.** The spike should test `qemu:///session` with user-mode networking and KVM. If it works, use it. If not, use system with a root-owned broker, a dedicated user, and a loopback-only app. The owner should decide after the spike, because the answer depends on the host.
* **One VM versus a second attacker VM.** The default is one target VM with a non-root actor. If the web targets cannot be made causal under that rule, a second minimal attacker VM is the fallback. The owner should decide after the PHP2Shell and GitLab validation paths are tested.
* **Single process versus web plus worker.** The default is one process with a background worker and a durable claim. The owner should choose after the kill-and-restart test.
* **LAN policy for the second user.** If both users are on the same workstation, loopback-only is enough. If one is remote, the token, Host allowlist, and TLS or SSH tunnel are required. The owner should state which case V1 supports.
* **GitLab version and resources.** The concept names the CVE but not the vulnerable Omnibus version. The owner or the advisory must pin a version that is actually vulnerable, and the pack must set memory and disk above the 4 GB / 40 GB defaults if the install needs it. If the CVE link does not identify the version, the job fails with `version_unidentified`.
* **Dirty Frag kernel source and shell driving.** The README names Ubuntu 24.04.4 with 6.17.0-23-generic. The draft must decide whether to use a prebuilt image, a kernel package stored at image-build time, or a custom image. It must also define the PTY wrapper and the exact root-only nonce proof, because the PoC may only spawn an interactive shell. If the kernel is not installable today, re-scope the target rather than substitute the host kernel.
* **Whether SQLite is needed at all in V1.** A job manifest plus JSONL and a directory listing may be enough for one or two users. SQLite earns its place when the job list, validator queries, or a second consumer appears. The owner should decide whether to start with the index or add it later.
* **Whether a `cves` table is needed.** A small fetch cache is defensible; a knowledge bank is not. The owner should decide whether the job manifest alone is enough.
* **Whether ADK survives the spike.** If the runner owns the sequence and the model needs only extraction and setup authoring, ADK may be a session store the design does not use. The owner should decide after the spike, and record the reversal of the old ADR 0007.
* **Web framework and live-log transport.** Server-rendered pages plus SSE is the smallest fit; polling a log file may be enough for one or two users. The draft can choose the framework; no SPA build chain is needed.
* **Deployment unit.** A systemd unit is the default; a manual virtual environment with a documented start command is acceptable for V1 if the host is a workstation. The owner should choose before the first long job.

### Staging

* **Phase 0: spikes, one week.** Three spikes run in parallel. (a) ADK plus LiteLLM plus DeepSeek with two tools, 20 scenarios, and a tool-call threshold. (b) libvirt session versus system, cloud-init, SSH, one Ubuntu VM, boot and destroy timings, an egress test, and a WSL2 restart check. (c) A hand-built PHP2Shell target in a VM, with a hand-written probe, to prove the environment and measure provisioning time. The phase fails if KVM is not stable, if ADK tool calling is unusable, or if the PHP build cannot be made repeatable. It also fixes the `VmDriver`, `GuestExec`, `HttpProbe`, and `LlmVerdict` interfaces.
* **Phase 1: engine and PHP2Shell, two to three weeks.** Build the job queue, state machine, event log, minimal SQLite index, fake VM driver, web UI shell with the four screens, SSE, cancellation, startup cleanup, and the target pack loader. Wire the model at extraction and setup authoring. Run PHP2Shell end to end with the runner-owned probe, the independent LLM validator, a fresh nonce, a null-actor check, and a frozen setup image. The verdict is stored as `llm_assessed`. Acceptance: two consecutive clean passes, a failed run with a reason code, a kill-and-restart test with no orphan, a dummy fourth pack that requires no pipeline edits, and a UI that shows state and verdict separately.
* **Phase 2: GitLab, two weeks.** Add the GitLab pack, the heavy provisioning path, the service health check, the nonce permission model, and the long-job UX. Acceptance: two consecutive clean passes, a queue that shows the long job, a cancel that cleans up, and no actor access to the nonce.
* **Phase 3: Dirty Frag, two weeks.** Add the pinned kernel, reboot and `uname -r` check, C build, PTY-driven root-shell validation with a root-only nonce, and mandatory destroy. Acceptance: two consecutive clean passes, a failure that still destroys the VM, and a `security_cleanup_failed` path that is visible.
* **Phase 4: hardening and acceptance, one week.** Run the prompt-injection corpus, the SSRF and CSRF tests, the secret-redaction check, the disk and token cap tests, the upgrade and rollback test, and the full audit reconstruction. Fix or explicitly accept each gap in the prior-failure table. Record the ADR that explains the reversals from the old tree.

The phases overlap only where the spikes feed the engine. Do not start Phase 2 before the PHP2Shell validation path and cleanup path pass, because GitLab will hide lifecycle bugs behind a long provisioning step.
