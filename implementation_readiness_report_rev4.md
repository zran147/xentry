### Registry id space is incomplete and has no image/artifact mapping - Severity: Blocker
* **Reviewer Lens:** `egm-implementation-readiness`, `egm-codebase-details`, `egm-style`
* **Affected Scope:** `xentry-v1.md` 204-229, 239, 245-247, 305; `xentry-v1-contracts.md` §1 lines 13-28, §3 lines 112-116, §5 lines 231-249, §10 lines 386-392
* **Discrepancy Description:** The registry lists only `ubuntu-24.04-target` and `ubuntu-24.04-attacker` images and only `ubuntu-target-image` / `ubuntu-attacker-image` artifacts, yet the Dirty Frag target requires `ubuntu-24.04-dirtyfrag` and §10 says that image is built. Image ids do not map to artifact ids: `Target.base_image_artifact_id` is validated as a registry artifact but the values table supplies image ids, while `create_target` takes an `image_id`. `Target.network_profile_id = isolated` is not one of the registered profiles (`target-php2shell`, `target-gitlab`, `target-dirtyfrag`, `attacker-remote`), even though unknown-profile calls are rejected. `build_poc` invokes `build-poc-*`, but no `build-poc-php` registry entry exists. `copy_in(vm_id, artifact_id, guest_path)` contradicts the rule that the broker chooses the destination path, and `http_probe` accepts a caller-supplied `target_ip` with no rule binding it to the job's managed network or target VM.
* **Rationale & Recommendation:** These ids are the broker's security boundary and its validation contract. With literal server-side rejection, valid `isolated`, `ubuntu-24.04-dirtyfrag`, and `build-poc-php` calls fail, and the implementer must invent ids and a mapping table. Publish one canonical registry table with image-id-to-artifact-id mapping, add the Dirty Frag image and `isolated` profile, add `build-poc-php` (or make `build_step_id` optional with an explicit skip), bind `target_ip` to `vm_id` or the managed network, and settle the `copy_in` destination rule. Add registry-completeness and off-network/path-traversal tests.

### Runner step table and probe execution are not an executable contract - Severity: Blocker
* **Reviewer Lens:** `egm-implementation-readiness`, `egm-codebase-details`, `egm-style`
* **Affected Scope:** `xentry-v1.md` 29, 249-280, 309-319; `xentry-v1-contracts.md` §1 lines 30-54, §4 lines 195-229, §6 lines 273-280
* **Discrepancy Description:** The main design lists 22 steps and combines `create_attacker + build_poc` at step 8; the contracts table has 23 separately numbered steps, and G3 in the main document already separates them. The table claims remote/local awareness but has no applicability, condition, cleanup, or failure columns, so `create_attacker`, `build_poc`, `destroy_attacker`, and `host_evidence` appear unconditional despite being target-conditional. Probe rows 13 and 17 use `probe-*` ids with "nonce id" parameters and user `broker`, while `http_probe` requires `network_id, target_ip, port, method, path, timeout, max_bytes`; `StepSpec.allowed_users` admits only `root` and `xentry-guest`; and nothing states whether a probe is an `exec` step or an `http_probe` call. `HttpResult` exposes only `body_sha256` / `body_excerpt` with no expected-nonce hash or `nonce_observed` flag, and no component is assigned to parse GitLab responses or host serial bytes. No row or action specifies who writes `job_outcomes` / the `jobs` projection, including failure paths that skip `validate`; the Dirty Frag note requires readiness and `uname -r` re-checks after the fresh boot but rows 14-15 contain no such step; `freeze` gives only "vm id" although snapshot requires a `kind` and remote restore must be memory-inclusive; and the Dirty Frag setup script builds the PoC inside a root step while step 9 builds it again as `xentry-guest`. Per-step ParamSpec names, types, and ranges are not enumerated, and `place_nonce` takes a `NonceRecord` in one signature and explicit id/path/owner/mode in another.
* **Rationale & Recommendation:** `runner.py` cannot be written without deciding which rows run per target, how probes are dispatched, what arguments they receive, how failure outcomes are projected, and which snapshot kind is taken. Adopt the contracts' 23-step table as the single list, add applicability/condition/cleanup columns, publish a probe dispatch table mapping `ProbeStep.kind` to `exec` or `http_probe` with full argument sources and a decisive-evidence output, assign the response/host-serial parser and the outcome projector, add the Dirty Frag post-boot readiness row, fix the remote snapshot kind to memory, and make the Dirty Frag PoC build single-owner.

### Target instances still lack required exact values - Severity: Blocker

* **Affected Scope:** `xentry-v1.md` 282-317, 618, 639; `xentry-v1-contracts.md` §3 lines 104-143, §5 lines 231-249
* **Discrepancy Description:** `Target` requires `nonce` (`NonceSpec{path, owner, mode}`), `probes` (`step_id`, `params`, `timeout_s`, exactly one `decisive`), `null_actor` (`location`, `step_id`), `poc` (`artifact_id`, `repository`, `commit`, `files`, `sha256`, `build_step_id`, `invocation_step_id`), `timeouts`, and `setup_sha256`, but §5 supplies only image, kernel, resources, attacker image, ports, actor, and PoC repository/branch. ### Retry and attempt semantics contradict each other - Severity: Major
* **Reviewer Lens:** `egm-codebase-details`
* **Affected Scope:** `xentry-v1.md` 280; `xentry-v1-contracts.md` §4 lines 199-229, §7 lines 282-321
* **Discrepancy Description:** Main line 280 says every retry starts a new attempt, while contracts line 229 says only a transient fetch retry or a PoC rerun creates attempt `N+1`. The step table assigns `retry: once` to `create_network`, `create_target`, `create_attacker`, `readiness`, `freeze`, `restore_or_reboot`, `probe`, and `destroy`, but never says whether those retries reuse the current attempt and `job_steps` rows or create a new attempt and rebuild the VM/network. * **Rationale & Recommendation:** The runner, queue, and audit index must know whether a retry is the same attempt or a new one and whether resources are preserved. Define a retry matrix covering retry class, attempt behavior, resource reuse/recreate, evidence, cleanup, and failure code.

### Phase/gate ordering is unsatisfiable as written - Severity: Major
* **Reviewer Lens:** `egm-implementation-readiness`, `egm-style`, `egm-codebase-details`

### Mirror and provisioning models contradict each other - Severity: Major
* **Reviewer Lens:** `egm-implementation-readiness`, `egm-style`, `egm-codebase-details`
* **Affected Scope:** `xentry-v1.md` 235-247, 605-606; `xentry-v1-contracts.md` §6 line 253, §10 lines 386-392
* **Discrepancy Description:** The main design says `config/packages.yaml` records the apt package set per target, that `apt-get download` from a pinned Ubuntu snapshot populates the mirror, and that the mirror serves the job's image/package/PoC manifest. Contracts §10 says the mirror is a static file server, "not an apt repository," and that apt packages are baked into the images; the setup scripts download only the PHP source, GitLab `.deb`, and kernel `.deb`. The two models imply different mirror contents, network policy, and `packages.yaml` purpose. * **Rationale & Recommendation:** Gate B checks mirror reachability under default-deny egress; an implementer could build an apt repository that requires unintended egress. Choose the baked-package model, delete or repurpose `config/packages.yaml` as an image-build manifest, define the exact mirror manifest contents and slot selection, and test that the mirror serves no `Packages.gz`/`Release` and that apt has no internet route.
